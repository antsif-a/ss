# 1. `src/main.cpp` — архитектура и полиморфизм

> `- Какие архитектурные принципы применены при реализации игры?`

**1. Расслоение по MVC.**
- Модель — `src/model` (`Rect`, `Movable`, `Collisionable`, `GameMap`,
  `MapMovable`) и `src/objects` (`Mario`, `Enemy`, `Ship`, `Box`,
  `FullBox`, `Money`).
- Представление — `src/ui/console` (`ConsoleGameMap`, `Console*`).
- Контроллер — игровой цикл в `main()` плюс `src/controller/game.cpp`
  и `src/levels`.

**2. Принцип инверсии зависимостей (Dependency Inversion).** Это главное
достижение проекта, и оно строже, чем просто MVC. Зависимости направлены
от конкретного к абстрактному: `Game` знает только про `Movable*`,
`Collisionable*`, `Rect*`, `MapMovable*` и **не знает ни одного
конкретного класса**. Обратная сторона: `ConsoleEnemy` наследует и
`Enemy`, и `ConsoleUIObjectRectAdapter` — то есть один объект
одновременно принадлежит предметной и отображающей иерархиям.

**3. Разделение интерфейса и реализации.** `UIFactory` /
`ConsoleUIFactory`, `KeyBoard` / `WindowsKeyBoard` / `LinuxKeyboard`,
`GameMap` / `ConsoleGameMap`.

**4. Единственная ответственность (частично).** `Game` отвечает только за
согласование объектов, `GameLevel` — только за расстановку объектов
уровня, `ConsoleGameMap` — только за отрисовку, `Logger` — только за лог.

**5. Открытость/закрытость.** Добавление нового уровня не требует правок
`Game` и игрового цикла — достаточно наследовать `GameLevel`.

> `- На основе какого принципа ООП построен алгоритм игры?`

**Полиморфизма.** Вся игра работает через единый интерфейс, а конкретное
поведение определяется типом объекта в момент вызова. Принципы 3 и 4 из
`README.md` — «логика работает с множествами абстракций» и
«используется полиморфизм» — это ровно одно и то же утверждение.

Второй по значимости — **наследование** как средство переиспользования
(`Enemy : RectMapMovableAdapter, Movable, Collisionable`), и третий —
**инкапсуляция** (`protected`-поля, `private`-конструктор у `Logger`).

> `- Какими элементами языка С++ реализуется этот принцип?`

- `virtual` и чисто виртуальные методы (`= 0`) — объявление интерфейса;
- абстрактные классы — классы с хотя бы одним `= 0`;
- указатели на базовые классы и динамическая диспетчеризация через vtable;
- `override` — защита от опечаток в сигнатуре;
- множественное наследование — для одновременного участия в нескольких
  иерархиях;
- `protected` / `private` / `public` — разграничение доступа;
- шаблонные методы (`get_brush()`, `get_rect()`), реализуемые в
  наследниках.

> `- Приведите примеры кода, отображающие этот принцип.`

**Пример 1. Главный цикл — одна строка на весь вектор объектов.**

```cpp
void Game::move_objs_horizontally() noexcept {
    for (Movable* obj: movable_objs) {
        obj->move_horizontally();      // динамически: вызов через vtable
    }
}
```
`Game` не знает, что в векторе. `Mario::move_horizontally()` (наследует
`Movable`, `hspeed == 0`) и `Enemy::move_horizontally()` (переопределяет
свою скорость) вызываются **одним и тем же кодом**.

**Пример 2. Реакция на столкновение выбирается объектом, а не контроллером.**

```cpp
obj->process_mario_collision(mario);
```
`Enemy::process_mario_collision` убивает врага, `FullBox::
process_mario_collision` — разрушает ящик и создаёт монету, `Money::
process_mario_collision` — исчезает, `Mario::process_mario_collision` —
пустая заглушка. Один вызов — четыре разных поведения.

**Пример 3. Уровень ничего не знает о представлении.**

```cpp
// src/levels/first_level.cpp
ui_factory->create_ship({20, 25}, 40, 2);
```
`FirstLevel` вызывает абстрактный `UIFactory`. Какой именно корабль
создастся — `ConsoleShip` — определяется на этапе сборки.

**Пример 4. Слой ввода полностью скрыт.**

```cpp
user_input = keyboard->get_user_input();
...
switch (user_input) { case biv::UserInput::MAP_LEFT: ... }
```

**Пример 5. Виртуальное наследование как проявление того же принципа.**

```cpp
class RectMapMovableAdapter : virtual public Rect, public MapMovable { ... };
class Movable : virtual public Rect { ... };
class ConsoleUIObjectRectAdapter : virtual public Rect, public ConsoleUIObject { ... };
```

# 2. `src/model/rect_map_movable_adapter.hpp`

> `- Почему класс Rect наследуется виртуальным образом?`

Потому что в `ConsoleEnemy` существуют **три независимых пути** к `Rect`:

1. `ConsoleEnemy` → `Enemy` → `RectMapMovableAdapter` → `Rect`
2. `ConsoleEnemy` → `Enemy` → `Movable` → `Rect`
3. `ConsoleEnemy` → `ConsoleUIObjectRectAdapter` → `Rect`

Это **ромб (diamond inheritance)**. При обычном наследовании в объекте
оказалось бы три отдельных подобъекта `Rect`, у каждого свои `top_left`,
`width`, `height`.

Последствия, если убрать `virtual`:

- **Неоднозначность.** `enemy.get_left()` — к какой копии обращаться?
  Ошибка компиляции `ambiguous base class`.
- **Расхождение состояния.** `RectMapMovableAdapter::move_map_left()`
  двигает `top_left.x` в **своей** копии `Rect`, а
  `ConsoleUIObjectRectAdapter::get_left()` читает `Rect::get_left()` из
  **другой**. Отрисовка в `ConsoleGameMap::refresh()` уехала бы от
  физики.

Ключевое правило C++: **виртуальным должно быть объявлено то наследование,
которое находится в вершине ромба** — то есть базовый класс. Промежуточные
классы объявлять виртуальными не нужно.

Следствие: инициализировать `Rect` обязан только конструктор самого
верхнего класса:

```cpp
ConsoleEnemy::ConsoleEnemy(const Coord& t, int w, int h)
    : Enemy(t, w, h) {}   // Enemy -> RectMapMovableAdapter -> Rect
```
А `ConsoleUIObjectRectAdapter` использует `= default` и не трогает `Rect` —
признак корректного виртуального наследования.

Полные диаграммы: `docs/diagrams.md`.

> `- Что такое паттерн адаптер?`

**Adapter (структурный паттерн).** Приводит существующий класс к
интерфейсу, который от него требует клиент, **не изменяя ни того, ни
другого**. Adapter бывает объектный (через наследование/композицию) и
классовый (через множественное наследование).

Классический пример: `std::stack` адаптирует `std::vector`, скрывая порядок
хранения. Схема:

```
клиент ──► интерфейс (Target) ◄── адаптер (Adapter) ──► Adaptee
```

> `- Для чего он применяется здесь?`

**1. `RectMapMovableAdapter` — адаптер объектной композиции.**
`MapMovable` требует два метода: `move_map_left()` и
`move_map_right()`. Но `MapMovable` ничего не знает о координатах. Адаптер
берёт на себя хранение позиции (наследуя `Rect`) и реализует требуемые
операции:

```cpp
void RectMapMovableAdapter::move_map_left()  noexcept { top_left.x -= MapMovable::MAP_STEP; }
void RectMapMovableAdapter::move_map_right() noexcept { top_left.x += MapMovable::MAP_STEP; }
```
Без него каждому объекту (кораблю, ящику, врагу, монете) пришлось бы
писать эти две строки у себя.

**2. `ConsoleUIObjectRectAdapter` — адаптер другого вида.**
`ConsoleUIObject` — интерфейс отрисовки, и он требует `get_left()`,
`get_top()`, `get_height()`. Но `get_height()` у `Rect` есть, а у
`ConsoleUIObject` ожидается именно **высота**, а `Rect` оперирует полем
`height` и методом `get_bottom()`. Адаптер приводит одну систему
имёнования к другой, ничего не меняя по сути:

```cpp
int ConsoleUIObjectRectAdapter::get_height() const noexcept { return Rect::get_height(); }
int ConsoleUIObjectRectAdapter::get_left()   const noexcept { return Rect::get_left(); }
```

Именно так работает принцип «логика независима от визуального
представления»: `Rect` не знает, что его когда-то нарисуют символом `#`.

> `- Какую ещё роль выполняет этот класс?`

Помимо адаптерации у `RectMapMovableAdapter` есть ещё несколько функций.

**1. Он же —Mixin (примесь).** `Ship` и `Box` от него **ничего не
добавляют**, только передают параметры в конструктор. То есть класс
существует ради «подмешивания» двух независимых возможностей — «быть
прямоугольником» и «реагировать на прокрутку карты» — в один класс.

**2. Он устраняет ромб.** Именно его объявление
`virtual public Rect` делает возможным множественное наследование в
`Enemy`, `Money` и консольных классах. Без него диаграммы из задания 1
пришлось бы перепроектировать.

**3. Он задаёт единое правило прокрутки.** `MAP_STEP = 1` и
±`top_left.x` описаны в одном месте. Если бы шаг прокрутки изменился,
менялся бы только этот класс.

**4. Он объединяет две системы отсчёта.** Объект существует сразу в двух
координатах: в своих собственных (`Rect::top_left`) и относительно
карты (смещается при прокрутке). Именно поэтому у `Mario` есть
`move_map_left()` / `move_map_right()`, которые двигают **не карту, а его
собственный `x`** — иначе он уехал бы с экрана.

# 3. `src/model/ui_factory.hpp`

> `- Какому паттерну проектирования соответствует UIFactory?`

**Абстрактная фабрика (Abstract Factory)** — в упрощённой форме.
`UIFactory` — абстрактный базовый класс-фабрика, `ConsoleUIFactory` —
конкретная реализация.

Строго по канону из «Погружение в паттерны проектирования» это **не
полноценный Abstract Factory**: у того должен быть **дерево** фабрик
(например, `ConsoleUIFactory` и `GraphicsUIFactory`, каждая со своим
семейством продуктов). Здесь конкретная фабрика ровно одна, а набор
создаваемых объектов фиксирован. Точнее назвать это **абстрактным
поставщиком продуктов** или **простой фабрикой с абстрактным
интерфейсом**.

Дополнительно каждый метод `create_*` — это **Factory Method**: он создаёт
продукт, скрывая конкретный тип. И заметно, что фабрика делает больше,
чем создаёт: она же **регистрирует** объект в `Game` и `GameMap` (см.
`docs/architecture.md`, раздел 3). Фактически это «фабрика + реестр»,
что размывает ответственность.

> `- В каких случаях используется этот паттерн проектирования?`

**Когда он полезен:**

1. **Система не должна зависеть от конкретной реализации.** Клиент
   работает с `UIFactory*` и не знает, будет ли вывод консольным,
   графическим или сетевым. Именно этот случай в проекте.
2. **Нужно создавать семейство связанных объектов**, гарантируя их
   совместимость. Здесь фабрика создаёт и объект, и все его регистрации
   в `Game` — несогласованное состояние невозможно по построению.
3. **Конкретная реализация определяется на этапе сборки**, а не в
   рантайме (макрос `LINUX_CONSOLE` / `WINDOWS_CONSOLE`).
4. **Централизация места, где объект «появляется в мире».** Удобно для
   отладки, логирования, учёта.

**Когда применять не стоит:**

- если объектов мало и они не связаны — фабрика станет лишним слоем;
- если нет вариантов реализации — абстракция «ради абстракции»;
- если состав продукта постоянно меняется — каждый раз придётся
  редактировать интерфейс.

**Недостатки текущей реализации:**

- **Нарушение OCP.** Добавление нового типа объекта требует изменить
  и `UIFactory` (добавить чисто виртуальный метод), и `ConsoleUIFactory`
  (реализовать его). Плюс `src/ui/console/ui_objects/CMakeLists.txt` и
  `src/util/CMakeLists.txt`.
- **Связаны создание и регистрация.** Нельзя создать объект, не
  зарегистрировав его. Иногда нужно и то, и другое независимо.
- **Нет `override`-защиты** у части методов в старых версиях
  (в `ConsoleUIFactory` все методы помечены `override` — это правильно).

# 4. `src/levels/game_level.hpp`

> `- На какую структуру данных похож класс GameLevel?`

**Односвязный список (linked list)** уровней, реализованный через
ссылки между объектами. Точнее — **связная цепочка уровней** с
полиморфным переходом.

> `- В чём это выражается?`

**1. Два указателя на соседей:**

```cpp
protected:
    GameLevel* parent = nullptr;
    GameLevel* next   = nullptr;
```

**2. Переход — чисто виртуальный метод:**
```cpp
virtual GameLevel* get_next() = 0;
```

**3. Реализация перехода:**

```cpp
// first_level.cpp
biv::GameLevel* FirstLevel::get_next() {
    if (!next) {
        clear_data();
        next = new biv::SecondLevel(ui_factory);
    }
    return next;
}

// second_level.cpp
biv::GameLevel* SecondLevel::get_next() { return next; }   // nullptr — конец
```

**4. Признак конца — тоже полиморфный:**
```cpp
virtual bool is_final() const noexcept;   // GameLevel -> false
bool SecondLevel::is_final() const noexcept override { return true; }
```

**5. Обход в игровом цикле:**
```cpp
if (game.is_level_end()) {
    if (!game_level->is_final()) {
        game_level = game_level->get_next();
        ...
    } else {
        game.finish();
    }
}
```

**Чем отличается от классического `std::list`:**

| | `std::list` | `GameLevel` |
|---|---|---|
| Где узлы | в контейнере | сами ссылаются друг на друга |
| Переход | `++it`, механизм контейнера | `get_next()` — **виртуальный вызов** |
| Кто решает, кто следующий | код обхода | **сам узел** |
| Список известен заранее | да | нет, строится лениво |

Именно последняя строка — суть. Каждый уровень **сам решает**, какой
уровень идёт следующим. Иначе в `main.cpp` пришлось бы писать
`switch` по номеру уровня, и добавление уровня ломало бы контроллер.
В терминах паттернов это совмещает **Linked List** с **Chain of
Responsibility**: `main` передаёт эстафету следующему уровню.

> `- Можно ли создавать экземпляры класса GameLevel и почему?`

**Нет, нельзя.** Работают сразу **два** механизма.

**1. Класс абстрактный.** Есть два нереализованных чисто виртуальных
метода:
```cpp
virtual GameLevel* get_next() = 0;
virtual void init_data()  = 0;
```
Попытка `new GameLevel(...)` или объявления `GameLevel level;` — ошибка
компиляции: «cannot instantiate abstract class».

**2. Конструктор `protected`:**
```cpp
protected:
    GameLevel(UIFactory*);
```
Даже если бы все виртуальные методы были реализованы, внешний код не
смог бы создать объект. Это **вторая линия обороны**: класс задуман как
«уровень не создаётся, а проектируется — наследник наполняет его
содержимым через `init_data`».

Также `protected`-поле `ui_factory` и конструктор, принимающий фабрику,
гарантируют, что любой уровень получит доступ к фабрике, не завися от
конкретного представления.

Также обратите внимание: `is_final()` **не** чисто виртуальный, у него
есть реализация по умолчанию `return false`. Это разумно: «уровень не
финальный» — поведение по умолчанию, иначе пришлось бы его дублировать
во всех уровнях. Чисто виртуальными объявлены только те операции, без
которых уровня не существует.

> `- В чём + и - конструкции GameLevel?`

**Плюсы:**

- **Единый контракт:** любой уровень гарантированно умеет `init_data()`,
  `get_next()`, `is_final()`, `restart()`.
- **Открытость/закрытость:** добавление уровня не требует правок в `Game`
  и в игровом цикле — только новый файл и строка в CMake.
- **Перенос выбора:** оператор «а какой уровень следующий» исчез из
  контроллера целиком.
- **Ленивое построение:** `SecondLevel` создаётся только когда игрок
  дошёл до финиша первого уровня.
- **Поле `parent`** — задел на переход к предыдущему уровню
  (например, для экрана «начать заново»).
- **Доступ к фабрике** у каждого уровня гарантирован конструктором, и
  уровень не зависит от представления.

**Минусы:**

- **Нет защиты от зацикливания.** Если `A::get_next()` вернёт `B`, а
  `B::get_next()` — `A`, игровой цикл зациклится. Проверки нет.
- **Нет защиты от `nullptr`.** `SecondLevel::get_next()` возвращает
  `next`, то есть `nullptr`. Сейчас это безопасно только потому, что
  `main.cpp` сначала проверяет `is_final()`. Стоит однажды забыть эту
  проверку — и будет разыменование `nullptr`.
- **Порядок вызовов.** `get_next()` у `FirstLevel` **сам** вызывает
  `clear_data()`. То есть смена уровня спрятана внутри «получения
  следующего» — неочевидный побочный эффект. Чище было бы
  `game_level->finish_and_get_next()`.
- **Поле `parent` не используется** нигде — мёртвый код.
- **Нет способа узнать номер или имя уровня**, что мешает сделать меню
  выбора уровня или HUD.
- **Утечка на перезапуске:** `restart()` → `clear_data()` →
  `ConsoleUIFactory::clear_data()`, который не удаляет объекты (см.
  `docs/architecture.md`, раздел 4). Каждая смерть Марио оставляет мусор
  в куче.

# 5. `src/objects/enemy.hpp` — ключевой вопрос задания 3

> `- Если создавать класс FlyableEnemy, JumpableEnemy и другие виды врагов, то почему их нельзя наследовать от Enemy?`

**Формально наследовать можно, но это будет некорректное
проектирование.** Причина в том, что поведение `Enemy` зашито в коде, а
не объявлено как абстракция.

**Проблема 1. Конструктор жёстко задаёт «ходьбу».**

```cpp
Enemy::Enemy(const Coord& t, int w, int h)
    : RectMapMovableAdapter(t, w, h) {
    vspeed = 0;
    hspeed = 0.2;          // ← ходьба с фиксированной скоростью
}
```
Летящий враг не должен иметь ходовой горизонтальной скорости, а
прыгающий на месте должен иметь `hspeed = 0`. При наследовании от
`Enemy` эти значения всё равно будут выставлены, и в теле конструктора
наследника придётся их **сбрасывать** — то есть сразу отменять
унаследованное поведение.

**Проблема 2. Метод называется не тем, чем является.**

```cpp
void Enemy::process_vertical_static_collision(Rect* obj) noexcept {
    top_left.x += hspeed;                        // заглянуть на край
    if (!has_collision(obj)) {
        process_horizontal_static_collision(obj); // края нет → развернуться
    } else {
        top_left.x -= hspeed;                    // край есть → отступить
    }
    if (vspeed > 0) { top_left.y -= vspeed; vspeed = 0; }
}
```
Это не «обработка столкновения», а **алгоритм обнаружения края
платформы**: враг оглядывается, не падает ли с корабля. Летящий враг
разворачиваться на краю не должен. Прыгающий на месте — тем более.

**Проблема 3. `Enemy` не абстрактный.**

Ни один метод не помечен `= 0`, класс можно создать. Поэтому компилятор
**не заставит** наследника переопределить неподходящее поведение.
Написав `class FlyableEnemy : public Enemy { };`, я получу врага, который
ходит, разворачивается на краях и имеет `hspeed = 0.2` — то есть
полностью неверного. И компилятор промолчит.

**Вывод.** `Enemy` — это не «любой враг», а конкретно «враг, который
ходит по платформам и разворачивается на краях». Название класса
слишком общее для его поведения.

### Как сделать правильно: выделить абстракцию

```cpp
class Enemy : public RectMapMovableAdapter, public Movable, public Collisionable {
    protected:
        // Скорость передаёт наследник: «ходит» — свойство WalkingEnemy.
        Enemy(const Coord& top_left, int width, int height, float hspeed);
        void land_on() noexcept;      // приземление, общее для всех

    public:
        // --- общее для всех врагов ---
        Rect get_rect() const noexcept override;
        Speed get_speed() const noexcept override;
        void process_horizontal_static_collision(Rect*) noexcept override;
        void process_mario_collision(Collisionable*) noexcept override;  // «кто погиб»

        // Шаблонный метод: сначала различающееся поведение, потом
        // приземление. Порядок критичен, см. ниже.
        void process_vertical_static_collision(Rect* obj) noexcept override {
            stand_on(obj);
            land_on();
        }

    protected:
        // --- различающееся: объявлено, но НЕ реализовано ---
        virtual void stand_on(Rect*) noexcept = 0;
};

class WalkingEnemy : public Enemy {  // текущая логика: ходьба + край
    protected: void stand_on(Rect*) noexcept override; };
class FlyableEnemy : public Enemy {  // гравитация выключена
    protected: void stand_on(Rect*) noexcept override;       // пусто
             void move_vertically() noexcept override; };
class JumpableEnemy : public Enemy {  // hspeed = 0, периодический jump()
    protected: void stand_on(Rect*) noexcept override; };
```

Различающееся поведение вынесено именно в `stand_on()`, а не в
`move_behaviour()`, потому что игровой цикл вызывает не «поведение
целиком», а конкретные хуки: `move_horizontally()`, `move_vertically()`
и `process_vertical_static_collision()`. Метод, который никто не
вызывает, был бы мёртвым кодом.

Теперь `Enemy` становится честно абстрактным: компилятор **обяжет**
каждого наследника определить своё поведение. Конструктор базового
класса перестаёт навязывать `hspeed = 0.2` — скорость становится
свойством конкретного подкласса.

### Важная деталь: порядок вызовов в `process_vertical_static_collision`

При разбиении на `stand_on()` и `land_on()` легко поставить
`land_on()` **первым** — кажется логичным («сначала приземлиться,
потом разбираться»). Это ломает ходячего врага, причём **молча**.

Проверка края опирается на `has_collision()`, а тот — на `get_bottom()`
(округление вниз). Пока враг ещё падает, его `bottom` на полклетки
больше, и он пересекается по вертикали с кораблём, на котором стоит:

| | кадр 10 | кадр 11 |
|---|---|---|
| порядок «сначала край» (как в оригинале) | `x=32.20`, идёт дальше | `x=32.40`, идёт дальше |
| порядок «сначала приземление» | `x=32.20` | `x=32.40`, **разворачивается** |

Во втором случае `land_on()` подтягивает `y` назад, `bottom` становится
равным `y` корабля, пересечения нет, `has_collision()` ложно, враг
решает, что стоит на краю, и разворачивается. Дальше это
повторяется каждый кадр: враг дрожит на месте вместо ходьбы.

Это проверяемо: траектории исходного `Enemy` и `WalkingEnemy` за 3000
кадров совпадают до четвёртого знака, а при неверном порядке —
расходятся с 11-го кадра.

Отсюда ещё одно следствие для `JumpableEnemy`: раз `stand_on()`
вызывается раньше `land_on()`, значение `vspeed` ещё не обнулено, а
`Movable::jump()` срабатывает только при `vspeed == 0` — прыжок молча
игнорируется. Поэтому наследник обязан обнулить скорость сам:

```cpp
void JumpableEnemy::stand_on(Rect*) noexcept {
    if (++frames_on_ground >= JUMP_PERIOD) {
        frames_on_ground = 0;
        vspeed = 0;   // land_on() вызвается позже и не поможет
        jump();
    }
}
```

**Альтернатива: композиция вместо наследования.**

```cpp
class MoveStrategy { public: virtual void step(Enemy*) noexcept = 0; };
class WalkStrategy   : public MoveStrategy { /* край + ходьба */ };
class FlyStrategy    : public MoveStrategy { /* синусоида */ };
class JumpStrategy   : public MoveStrategy { /* прыжки */ };
```
`Enemy` при этом **вообще не трогаем** — новые классы не наследуются от
него, а используют общие части (`RectMapMovableAdapter`, `Movable`,
`Collisionable`) и поле-стратегию.

**Сравнение подходов:**

| | Промежуточный абстрактный класс | Стратегия (композиция) |
|---|---|---|
| Правки в `enemy.hpp` | нужны (сделать абстрактным) | **не нужны** |
| Дублирование общего кода | нет | есть (`get_rect`, `get_speed`, `process_mario_collision` ≈ 15 строк) |
| Лишний уровень косвенности | нет | да (вызов через указатель) |
| Соответствует ответу на вопрос | **да** — прямо показывает, что «нельзя» | частично |
| Расширяемость | новый враг = новый подкласс | новый враг = новая стратегия + класс |

**Рекомендация для задания 3:** промежуточный абстрактный класс. Это
прямой ответ на поставленный вопрос и меньше всего дублирования.
Правки сводятся к добавлению одного чисто виртуального метода в
`enemy.hpp` и переносу старой логики в `WalkingEnemy` — то есть это
*переработка*, а не переписывание.

# 8. `src/util/format.cpp`

> `- К какому виду функций принадлежит format_string(const std::string& format, T first, Args... rest)?`

Четыре характеристики:

**1. Шаблонная функция (function template).**
```cpp
template<typename T, typename... Args>
std::string format_string(const std::string& format, T first, Args... rest);
```

**2. Вариативный шаблон (variadic template, C++11).** Параметр
`typename... Args` принимает произвольное число дополнительных
аргументов произвольных типов.

**3. Рекурсивная функция.** Рекурсия идёт по пакету:
```cpp
return format_string(result, rest...);
```
Каждый вызов «съедает» один аргумент и один `{}`.

**4. Перегрузка + рекурсивное семейство шаблонов.** В паре с
нешаблонной перегрузкой
```cpp
std::string format_string(const std::string& format);
```
получается классическая схема **рекурсивных шаблонов**: нешаблонная
версия — **базовый случай** (пакет пуст, возвращаем строку как есть),
шаблонная — **рекурсивный шаг**. Разрешение перегрузки выбирает нужную
на каждом шаге.

Плюс: это пример **статического (компиляторного) полиморфизма** —
поведение зависит от типов аргументов, известных на этапе компиляции.

> `- В чём + и - таких функций?`

**Плюсы:**

- не нужно заранее знать количество и типы аргументов;
- **типобезопасность**: каждый аргумент выводится через `operator<<`,
  опечатка в типе — ошибка компиляции, а не падение в рантайме;
- читаемость: `format_string("x={}", 42)` вместо `printf`-стиля;
- легко расширяется: любой тип с `operator<<` работает автоматически;
- проверка количества аргументов на этапе компиляции — сколько
  передали, столько и подставится (в пределах явных инстанцирований,
  см. раздел 9).

**Минусы (для этой реализации конкретно):**

- **Рекурсия.** N аргументов → N+1 вызовов, каждый со своим
  `std::ostringstream`. Это заметно дороже `printf`.
- **Строка собирается многократно.** На каждом шаге создаётся новая
  строка через `substr` + конкатенацию — O(N²) по длине результата.
- **Ошибки не диагностируются.** Если `{}` больше, чем аргументов,
  «лишние» просто останутся в строке. Если меньше — лишние аргументы
  молча проигнорируются (`return format`).
- **Поддерживается только `{}`.** Никаких `{:>5}`, `{:.2f}`, `{:x}` —
  то, ради чего обычно и нужен форматированный вывод.
- **Нет индексации аргументов.** Нельзя использовать один аргумент
  дважды (`format_string("{} {}", x, x)` — придётся передать дважды).
- **Не потокобезопасно** при использовании глобальных буферов (здесь
  буферы локальные, так что это не проблема).
- **Глубина рекурсии** ограничена стеком — для тысяч аргументов
  переполнение.

> `- Что такое Args...?`

**Параметр-пакет (parameter pack), C++11.** Это конструкция, позволяющая
функции или шаблону принять произвольное число аргументов.

```cpp
template<typename T, typename... Args>
std::string f(const std::string& s, T first, Args... rest);
//                          ^^^^^^^        ^^^^^^^^^^^^^^
//                          один «лишний»   пакет значений
```

Разберём по частям:

| Элемент | Смысл |
|---|---|
| `typename... Args` | **пакет типов** — последовательность типов неизвестной длины |
| `Args... rest` | **параметр-пакет значений** — последовательность аргументов |
| `T first` | обязательный первый аргумент; нужен, чтобы остановиться на непустом пакете |
| `sizeof...(Args)` | количество аргументов в пакете (здесь не используется) |

**Важные свойства:**

1. **Пакет должен быть последним параметром** функции. Поэтому
   обязательный `first` вынесен перед ним.
2. **Пакет разворачивается (pack expansion) оператором `...`:**
   `format_string(result, rest...)` — «передать все элементы пакета
   по одному».
3. **Пакет может быть пустым.** Тогда `Args...` — ноль типов, и
   разрешение перегрузки выберет нешаблонную версию-базовый случай. Это и
   завершает рекурсию.
4. **Пакет типов vs пакет значений** — разные сущности: `Args` — типы,
   `rest` — значения. Они всегда появляются вместе и «разворачиваются
   синхронно».
5. **Совершенная пересылка (perfect forwarding)** требует другого вида
   параметра:
   ```cpp
   template<typename T, typename... Args>
   void f(T&& first, Args&&... rest);          // ссылки
   f(std::forward<Args>(rest)...);              // пересылка
   ```
   Здесь используется `Args... rest` (передача **по значению**) — проще,
   но лишние копии строк.

**Аналогия:** `Args...` — это «список покупок» неизвестной длины, который
передаётся функции. Функция берёт по одному предмету (`first`), а
остальные передаёт дальше (`rest...`), пока список не опустеет.

# 9. `src/util/format_templates.cpp`

> `- Зачем нужен этот файл?`

**Проблема, которую он решает.** Определение шаблона находится в
`.cpp`, а объявление — в `.hpp`:

```cpp
// format.hpp
template<typename T, typename... Args>
std::string format_string(const std::string& format, T first, Args... rest);

// format.cpp
template<typename T, typename... Args>
std::string biv::format_string(const std::string& format, T first, Args... rest) { ... }
```

Компилятор генерирует код шаблона **в той единице трансляции, где
видится определение**. Файл `logger.cpp` видит только объявление, поэтому
вызов `format_string<int>(...)` компилируется, но тела функции у него
нет. На этапе линковки возникает `undefined reference`.

**Решение** — явная инстанциация:

```cpp
// format_templates.cpp
#include "format.hpp"
#include "format.cpp"          // подключаем ОПРЕДЕЛЕНИЕ

template std::string biv::format_string<int>(const std::string&, int);
template std::string biv::format_string<std::string>(const std::string&, std::string);
```

`#include "format.cpp"` делает определение видимым, а следующие две
строки **явно требуют сгенерировать** код ровно для двух типов. Именно
эти два типа нужны макросу `LOG_INFO`.

Обратите внимание, что в `src/util/CMakeLists.txt` в `target_sources`
перечислен **только** `format_templates.cpp`, а `format.cpp` — нет.
Это не oversight, а необходимость (см. ниже).

**Почему это плохое решение:**

- **Ручное перечисление типов.** Забыли добавить `long` — получите
  ошибку линковки вместо ошибки компиляции.
- **Поддерживается ровно один аргумент.** Проверено экспериментально:
  ```
  format_string("x={}", 42)            → линкуется   (это format_string<int>)
  format_string("s={}", std::string)   → линкуется   (это format_string<std::string>)
  format_string("{} and {}", 1, 2)     → ОШИБКА ЛИНКОВКИ:
      undefined reference to
      biv::format_string<int, int>(const std::string&, int, int)
  ```
  Два аргумента дают **другую специализацию** `format_string<int, int>`,
  для которой явной инстанциации нет. То есть `LOG_INFO("{} {}", a, b)`
  **не собирается**.
- **Спасла только неиспользуемость.** `LOG_INFO` не вызывается нигде в
  проекте — ограничение ни разу не проявилось.
- **Хрупко.** Любое переименование сигнатуры в `format.hpp` без правки
  `format_templates.cpp` даёт ошибку линковки.

> `- Какие есть варианты реализации без такого подхода?`

**(а) Перенести определение в заголовок** — классический путь.
```cpp
// format.hpp
template<typename T, typename... Args>
std::string format_string(const std::string& format, T first, Args... rest) { ... }
```
+ Просто, работает всегда, поддерживает любое число аргументов.
− Определение видно во всех единицах трансляции; время компиляции и
объём объектных файлов растут (хотя компилятор генерирует код только для
используемых специализаций).

**(б) `inline` на определении в `.cpp` + `extern template` в `.hpp`.**
```cpp
// format.hpp
extern template<typename T, typename... Args>
std::string format_string(const std::string&, T, Args...);
```
+ Явно фиксирует «здесь только объявление», линковка чистая.
− Всё равно нужен отдельный `.cpp` с определением и ручным перечислением
типов для явных инстанцирований.

**(в) Отказ от шаблонов: `std::ostringstream` напрямую.**
```cpp
std::ostringstream oss;
oss << "x=" << 42 << " y=" << 3.5;
```
+ Самое простое и быстрое, компилятор всё проверит, ноль рекурсии.
− Нет строкового формата `{}`, нужно писать `<<` вручную, ленивые
аргументы вычисляются всегда.

**(г) `std::format` (C++20).**
```cpp
std::format("x={} y={:.2f}", 42, 3.5);
```
+ Стандарт, проверка на этапе компиляции, форматирование, без рекурсии.
− Требует C++20. В проекте `CMAKE_CXX_FLAGS` задаёт только charset,
стандарт не указан, значит берётся по умолчанию (для современного GCC
это C++17) — придётся явно добавить `-std=c++20`.

**(д) Внешние библиотеки:** `fmt` (или `spdlog`, которая его использует).
`fmt::format("x={}", 42)`. + Проверено годами, поддерживает все типы.
− Внешняя зависимость, нужно подключать через CMake/Conan.

**(е) `printf`-стиль с `varargs` (`<cstdarg>`).**
+ Максимальная скорость.
− **Типонебезопасно**, не соответствует идее проекта (C++ вместо C),
ломается при передаче `std::string` или `float`.

> `- В чём + и - всех подходов?`

| Подход | Аргументов | Типобезопасность | Форматирование | Сложность | Зависимости |
|---|---|:---:|:---:|---|:---:|
| Текущий (явная инстанциация) | **только 1** | да | нет | средняя | нет |
| Определение в `.hpp` | любое | да | нет | низкая | нет |
| `ostringstream` вручную | любое | да | нет | низкая | нет |
| `std::format` (C++20) | любое | да | **да** | нулевая | C++20 |
| `fmt` / `spdlog` | любое | да | **да** | нулевая | внешняя |
| `printf` | любое | **нет** | да | низкая | нет |

**Вывод для защиты:** текущий подход выбран, чтобы не засорять заголовок
определением шаблона, но ценой стало искусственное ограничение в один аргумент
и ошибка линковки вместо ошибки компиляции. Для учебного проекта,
где `LOG_INFO` не используется, это безвредно; в рабочем коде —
неприемлемо.

**Дополнительно: что будет, если добавить `format.cpp` в
`target_sources`?** (вопрос задан комментарием в
`src/util/CMakeLists.txt`)

Ответ — **ошибка линковки: повторное определение функции**. Проверено
экспериментально:

```
/usr/bin/ld: повторное определение «biv::format_string(std::string const&)»;
format_templates.cpp: здесь первое определение
/usr/bin/ld: format.cpp: здесь первое определение
collect2: error: выполнение ld завершился с кодом возврата 1
```

Причина: `format_templates.cpp` делает `#include "format.cpp"`, то есть
**текстовое включение**. Нешаблонная перегрузка
`std::string biv::format_string(const std::string&)` — обычная функция,
она не `inline` и не в анонимном пространстве, поэтому определяется
одинаково в двух объектных файлах. Символ не является «слабым», и линкер
ругается.

Как починить, не убирая `#include`: объявить функции `inline`. Тогда
несколько определений в разных единицах трансляции законны — линкер
выберет одно. Но правильный ответ здесь другой: `format.cpp` **не должен**
быть в списке исходников, потому что он и так включён в
`format_templates.cpp`. Этот `.cpp` — не самостоятельная единица
трансляции, а «придаток» к `format_templates.cpp`.

# 10. `src/util/logger.hpp`

> `- В стиле какого паттерна проектирования написан этот класс?`

**Singleton (Одиночка)**, конкретно — **Meyers Singleton**
(реализация через статическую локальную переменную, стандарт C++11).

`Logger` соответствует всем признакам паттерна:
- приватный конструктор → объект нельзя создать снаружи;
- статический метод `getInstance()` → единственная точка доступа;
- удалённые копирование и перемещение → нельзя сделать второй экземпляр
  копированием.

Это один из четырёх паттернов, заявленных в `README.md` (наряду с
Factory, Adapter и Iterator).

> `- Почему здесь использован этот паттерн?`

**1. Логирование — процесс, который должен быть один.** Несколько
экземпляров означали бы несколько файлов `super_mario_log.log` или
несколько буферов, дерущихся за один дескриптор.

**2. Нужен доступ из любой точки, без передачи.** Макрос `LOG_INFO`
разворачивается в `biv::Logger::getInstance()`. Если бы требовалось
передавать экземпляр по параметрам, сигнатура каждой функции
зависела бы от логирования. Логирование — **сквозная** функциональность,
и Singleton убирает её из сигнатур.

**3. `std::ofstream` не копируется.** У экземпляра есть
`std::ofstream log_file` и `std::mutex log_mutex`, оба запрещают
копирование. Нужен механизм, дающий ** ссылку** на единственный
объект.

**4. Файл открывается один раз** (с `std::ios::trunc`) — повторное
открытие затёрло бы лог в начале игры.

> `- Что такое LOG_INFO и для чего он сделан?`

```cpp
#define LOG_INFO(...) biv::Logger::getInstance().log_info(biv::format_string(__VA_ARGS__))
```

Это **макрос препроцессора**, а не функция. Он делает три вещи:

**1. `__VA_ARGS__`** — «кvariadic-аргументы» макроса (C++11). В
препроцессоре `...` в списке параметров означает «сколько угодно
аргументов», а `__VA_ARGS__` подставляет их обратно через запятую.

**2. `biv::format_string(__VA_ARGS__)`** — вызов шаблонной функции из
раздела 8, которая подставляет значения в строку с `{}`.

**3. `Logger::getInstance().log_info(...)`** — получение единственного
логгера и запись сообщения.

**Экспансия.** Вызов
```cpp
LOG_INFO("Mario at ({}, {})", mario->get_x(), mario->get_y());
```
превращается в
```cpp
biv::Logger::getInstance().log_info(
    biv::format_string("Mario at ({}, {})", mario->get_x(), mario->get_y())
);
```

**Зачем макрос, а не функция:**

- **Коротко.** `LOG_INFO("...")` вместо трёх уровней вложенности.
  Внутри макроса уже используется шаблон, который сам прячет ввод.
- **Доступ к приватному конструктору не нужен** — макрос идёт через
  публичный `getInstance()`.
- **Не требует `std::string` на месте вызова** — `format_string` вернёт
  `std::string` из строкового литерала.
- **Не тянет `<iostream>`/`<sstream>`** в каждое место вызова.

**Недостатки подхода:**

- **Нет проверки типов.** Ошибка в имени метода или в количестве
  `{}` вылезет как ошибка линковки или как «лишний `{}` в логе», а не
  как ошибка компиляции.
- **Отладчиком не видно.** В стеке вызовов — `log_info`, а не
  `LOG_INFO`.
- **Аргументы вычисляются на каждый вызов** (здесь ровно один раз, так
  что корректно).
- **Нет именованных параметров и уровней** (нет `LOG_WARN`,
  `LOG_ERROR`).
- **Стандартная альтернатива** — `inline` шаблонная функция:
  ```cpp
  template<typename... Args>
  void log_info(std::string_view fmt, Args&&... args);
  ```
  Она типобезопасна, отлаживается и позволяет добавить проверку формата.

> `- Зачем в классе КпоУ и деструктор сделаны private, а КК, КП, ОПК, ОПП удалены?`

Сначала расшифрую сокращения:
**КпоУ** — конструктор по умолчанию, **КК** — конструктор копирования,
**КП** — конструктор перемещения, **ОПК** — оператор присваивания
копирования, **ОПП** — оператор присваивания перемещения.

### Зачем конструктор и деструктор `private`

Это **первая линия обороны** паттерна Singleton: запретить создание
объекта снаружи класса.

- **`private` конструктор** — нельзя ни `Logger l;`, ни
  `new Logger()`. Единственный законный путь — внутри самого класса, то
  есть в `getInstance()`.
- **`private` деструктор** — нельзя `delete` указатель на `Logger` извне
  и нельзя создать объект в области видимости стека (уничтожение
  вызвало бы приватный деструктор).

Вместе они гарантируют: **единственный экземпляр создаётся и
уничтожается только самим классом.** А экземпляр, как известно, ровно
один.

Обратите внимание на достоинство: `~Logger()` выполняет реальную работу —
пишет «Game shutting down» и закрывает файл. Приватный деструктор
дополнительно гарантирует, что эта логика сработает **ровно один раз**,
при выходе из программы.

### Зачем остальные четыре удалены, а не сделаны `private`

**Это разные механизмы, и разница важна:**

| | `= delete` | `private` |
|---|---|---|
| Доступ | формально **открыт** | **закрыт** |
| Диагностика | `call to deleted function` — точно и по делу | `access to ... is private` — менее конкретно |
| Намерение | «эта операция **не существует** в принципе» | «она существует, но вызвать её нельзя» |
| Можно ли унаследовать | да (наследник не сможет её определить) | нет (наследник тоже не сможет) |

Для случая «экземпляр нельзя копировать» правильно именно `= delete`:
операция **не имеет смысла**, и компилятор скажет об этом прямо.

**Конкретные причины:**

1. **`std::ofstream` не копируется.** Стандарт запрещает копирование
   потоков файлов. Попытка скопировать `Logger` упрётся в `ofstream`, и
   без `= delete` пользователь получил бы каскад непонятных ошибок внутри
   `basic_filebuf`.
2. **`std::mutex` не перемещается.** Перемещение логгера сдвинуло бы
   `log_mutex` и **сломало бы синхронизацию**: два объекта, думающих, что
   они владеют одним и тем же мьютексом. Это уже не «неудобно», а
   небезопасно.
3. **Копирование сломало бы паттерн.** Даже если бы `ofstream` копировался,
   получилось бы два «единственных» логгера.
4. **Семантика запрета лучше выражает намерение.** Копирование
   `Logger` — не «внутреннее дело», которому просто закрыт доступ, а
   операция, которой **не должно существовать**.

**Альтернатива, которую тоже можно назвать классической:**
```cpp
private:
    Logger(const Logger&);            // просто private
    Logger& operator=(const Logger&);
```
Синтаксически работает так же. Но `= delete` точнее, и в современном C++
предпочитается именно он.

**Отдельная деталь про `getInstance()`:** возвращается **ссылка**
`Logger&`, а не указатель. Поэтому при обращении `Logger::getInstance()`
копирования не происходит. Но если бы кто-то написал
```cpp
Logger l = Logger::getInstance();     // попытка скопировать
```
то сработал бы запрет — с понятным сообщением, а не с попыткой
скопировать `ofstream`.

# 11. `src/util/logger.cpp`

> `- Почему instance является статической локальной переменной?`

```cpp
Logger& Logger::getInstance() {
    static Logger instance;
    return instance;
}
```

Это и есть **Meyers Singleton**. Статическая локальная переменная внутри
функции выбрана по четырём причинам.

**1. Потокобезопасность «бесплатно» с C++11.** Стандарт гарантирует, что
инициализация статической локальной переменной выполняется **ровно
один раз**, даже если `getInstance()` вызывается из нескольких потоков
одновременно. На уровне машинного кода компилятор обычно реализует это
через compare-and-swap (поэтому в отладчике рядом видна проверка, похожая
на «magic statics»). Никакого явного мьютекта не нужно.

**2. Ленивая инициализация.** Файл `super_mario_log.log` создаётся при
**первом** обращении к `getInstance()`, а не при запуске программы. Если
логирование не понадобится, файл и не появится.

**3. Гарантированный вызов деструктора.** Статические локальные
переменные уничтожаются в **конце программы**, в обратном порядке
создания. Это работает и тогда, когда логгер создан лениво, — при
нормальном завершении `main` или при `exit`. Именно поэтому `~Logger()`
успевает дописать «Logger shutting down. Game finished.» и закрыть
файл.

Сравните с глобальной переменной в `.cpp`:
```cpp
Logger Logger::instance;          // инициализируется ДО main
extern Logger Logger::instance;   // + объявление в заголовке
```
У глобального объекта время жизни — тоже до `main`, но есть две
проблемы: (а) файл откроется даже без единой записи; (б) **не определён
порядок разрушения** относительно других глобальных объектов, и при
выходе может возникнуть «destruction of X while Y is still alive».

**4. Соблюдается приватность конструктора.** `static Logger instance;`
находится внутри функции-члена класса, поэтому законно вызывает
приватный конструктор. Объявить глобальный экземпляр `Logger` вне
класса было бы невозможно (private-конструктор) — а объявить
`static Logger Logger::instance;` как член класса нельзя, потому что у
`Logger` нет конструктора по умолчача, доступного извне.

**Что не получится:**

- `getInstance` с указателем (`if (!instance) instance = new Logger;`) —
  не потокобезопасно;
- отказ от синхронизации ради скорости — недопустимо, гонка создаст два
  логгера;
- `thread_local` — нужен ровно один на процесс, а не на поток;
- два экземпляра «для удобства» — смысл паттерна утрачен.

**Что можно улучшить:** разовое `new` в функции-члене с
`static std::unique_ptr<Logger>` — эквивалент по смыслу, хуже по
формальному соответствию определению «Singleton». А вот вариант с
**немедленным** созданием (глобальный объект) — допустим, если заранее
известно, что логирование нужно всегда: он убирает проверку из
`getInstance()` совсем, но переносит стоимость в загрузку программы и
теряет ленивость.

> `- Как реализовать getInstance() без многопоточности?`

Если многопоточность **не нужна** вовсе, достаточно обычной глобальной
переменной:

**Вариант 1. Глобальный экземпляр в `.cpp`.**
```cpp
// logger.cpp
Logger Logger::instance;
// logger.hpp (в классе)
static Logger instance;
static Logger& getInstance();
```
Вызов без проверок. Но: лог откроется при старте программы даже без
записей, и появляется риск порядка инициализации глобальных объектов
(«static init order fiasco»), если другие глобальные переменные
попытаются записать в лог из своих конструкторов.

**Вариант 2. Глобальный указатель + ленивая инициализация.**
```cpp
// logger.cpp
Logger* Logger::instance = nullptr;

// logger.hpp
static Logger* instance;

Logger& Logger::getInstance() {
    if (instance == nullptr) {
        instance = new Logger();
    }
    return *instance;
}
```
Это и есть классический Singleton из учебников: поле проверяется на
`nullptr`, при первом вызове создаётся объект, в поле записывается
указатель. Синтаксически проще и быстрее, чем текущий код, — нет
скрытой проверки инициализации на каждом вызове.

**Цена этого варианта — та же проблема, только явная:**

```cpp
// Поток 1                          // Поток 2
if (instance == nullptr)            if (instance == nullptr)          // оба видят nullptr
    instance = new Logger();            instance = new Logger();       // создают ДВА логгера
```

Это **гонка состояний (race condition)**. Обнаружить её почти
невозможно: программа работает, файлы создаются, но иногда
записываются не туда, а `delete` одного экземпляра сделает второй
висячим указателем. Классические «костыли» этого не чинят, а маскируют.

**Что показательно для защиты:** именно поэтому в задании отдельно
спрашивается, почему `instance` — статическая **локальная**
переменная. Сравнение должно быть таким:

| | Глобальная `Logger` | `static Logger*` + `new` | `static Logger instance` |
|---|---|---|---|
| Ленивая инициализация | нет | да | да |
| Потокобезопасность | гарантирована (но не лениво) | **нет** | **да, с C++11** |
| Уничтожение | при выходе | **вручную**, иначе утечка | гарантированно |
| Приватный конструктор | нарушается | нарушается | соблюдается |
| Соответствует паттерну | приблизительно | классически | по канону |

**Отдельно про `new`:** вариант 2 теряет вызов деструктора — объект
никогда не удаляется, файл не закрывается явно. Текущий вариант со
статической локальной переменной выигрывает и здесь.
